# Threat model

## Assets

- AWS evidence collected during assessment.
- Findings and risk scores generated by the detection engine.
- Approval records and their hash values.
- SQLite ledger entries for approvals and session reuse.
- Remediation execution paths and evidence verification logic.
- Terraform and GitHub workflow trust configuration.

## Trust boundaries

- CI/CD boundary: GitHub Actions OIDC is treated as a separate boundary from runtime access.
- Local runtime boundary: Python project and local SQLite files remain on the developer workstation.
- AWS boundary: all assessment, remediation, and bootstrap actions are assumed to be outside this source-only validation until authorized.

## Threat actors

- Malicious or compromised repository contributor.
- Malicious or compromised workflow execution.
- Local attacker with filesystem access to the repository state.
- Unauthorized operator attempting to replay or alter approvals.

## Abuse cases

### Approval forgery

An attacker may attempt to create an approval for a different action or target. The project counters this with approval hash binding and strict validation of action, target, and rationale.

### Approval replay

A previously consumed approval must not be reused. The SQLite ledger prevents replay and the workflow enforces checked consumption before a success state is returned.

### Resource substitution

A malicious actor may substitute a different resource for the target during execution. The validation layer rejects mismatches between the approval target and the actual resource used in verification.

### Stale evidence

Old evidence can make a remediation appear valid when it is not. The project rejects stale evidence based on timestamp checks and requires a fresh assessment session.

### Privilege escalation

Allowlisted remediation actions are intentionally narrow and do not permit broad role mutation or arbitrary IAM admin actions.

### Compromised CI/CD workflow

The OIDC identity path avoids static long-lived credentials. The workflow requires explicit confirmation before AWS role assumption is attempted.

### Malicious repository changes

The repo remains a source review and local validation package. Live AWS operations are explicitly blocked until approval. No cloud mutation occurs in this workspace.

### Audit record tampering

The project uses a durable SQLite ledger for approval and session use. The design is not meant to replace a full immutable audit system, but it is designed to make replay and session reuse difficult to achieve.

### Database unavailability

If the database is unavailable or a transaction fails, the application enters a fail-closed state rather than falsely claiming success.

### Incomplete cleanup

The project documents a separate bootstrap and cleanup identity to keep test teardown distinct from runtime security operations.

## Security controls

- Allowlist enforcement for remediation actions.
- Approval hash binding to action target and reasoning.
- Atomic SQLite transaction boundaries.
- Reuse checks for approvals and assessment sessions.
- Fresh-evidence verification gate.
- No static AWS keys in the default deployment workflow.
- Explicit human approval required for role assumption.

## Residual risks

- The project is not live AWS-validated.
- The current SQLite ledger remains local and is not a hardened immutable audit store for production-grade compliance.
- Future live AWS sandbox execution must be independently reviewed, costed, and cleaned up with separate bootstrap/cleanup controls.
